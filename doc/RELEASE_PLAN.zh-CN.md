# Stalltrace 首版开源规划

建议将 Stalltrace 定位为可嵌入 Flutter 应用的 Android 前台卡顿诊断插件。首版交付标准是，接入方能在自己的 release 包中，从一次系统确认的输入 ANR 追到对应的 Dart 或 Native 源码行，并看清这次归因的依据。发布日期以真机和兼容性验收结果为准。

## 已确认的首版决定

| 决定 | 建议 | 对首版的影响 |
| --- | --- | --- |
| 支持范围 | Android 优先；混合栈支持 ARM64、release AOT、root isolate 与平台线程合并。Android 24 起采卡顿，30 起读取系统历史 trace。 | 可以发布明确的兼容矩阵。拆分线程、多 isolate、后台 ANR 和 iOS 卡死诊断分别立项。 |
| 接入与数据 | 显式启动，私有目录落盘，符号化在开发机或接入方 CI 完成。保留独立的卡顿、系统确认和未知状态。 | 接入方掌握符号和报告。开发版保留能力与目录，并提供报告枚举及按条删除 API。 |
| 开源归属 | 项目名 Stalltrace，包名 `stalltrace`，使用 MIT 许可证；GitHub 仓库为 arkin1614-code/stalltrace，pub.dev 发布身份待确认。 | 维护者已授权公开源码并运行 GitHub CI。pub.dev 正式发布仍在真机验收后进行。2026-11-25 精确查询 pub.dev 包接口返回 404；名称没有预留。 |

## 当前可 review 的实现

`lib/stalltrace.dart` 提供 `Stalltrace.start()`、`Stalltrace.stop()` 和能力返回值。Android 插件监听宿主 Activity 生命周期，复用进程级采样器，后台写入主线程样本，并在 API 30+ 导入本进程可用的历史 trace。`tool/symbolize.py` 校验 Build ID 并独立解析两种来源。`example/` 作为普通 path 依赖接入，阻塞注入和手工导出只存在于示例中。

原型阶段在 API 37 模拟器上确认了四次输入 ANR。2026-11-25 对独立插件重新运行三个用例，使用 Flutter 3.47.9 的 ARM64 release 示例、无 Dart 混淆。以下数据仅来自插件复验。

| 用例 | 系统 ANR 事件数 | 命中预设函数的现场样本 | 系统 trace |
| --- | ---: | ---: | --- |
| 18 秒 Dart 计算 | 1 | 9/9，最近样本距系统事件 622 ms | 独立还原到 Dart 计算函数及其调用者 |
| 18 秒同步 FFI 等待，7 秒后注入输入 | 1 | 9/9，最近样本距系统事件 318 ms | 独立还原到 C 等待函数、C 入口和 Dart 调用者 |
| 2.3 秒短卡顿 | 0 | 1/1 | 阻塞期间无系统 ANR 事件 |

静态检查、两个 Dart 接口测试、一个示例页面测试及干净源码构建均已通过。示例与验收命令见 [复现说明](../example/README.md)。完整原始设备输出仅保存在本地。模拟器上的两个正例尚不足以估算线上召回率。

## 发布前值得盯住的三个失败场景

- **系统 trace 缺失或抓晚。** 保留现场样本、时钟和来源。关联缺少唯一证据时保留“不确定”，把可确认与不可确认事件分开统计。
- **宿主已有采样 SDK，或库缺少可展开帧。** 验证信号共存、超时、截断及降级行为。验收要包含一个纯 Native 阻塞，确保没有 Dart 业务帧时不会补出伪帧。
- **公开材料泄露现场信息。** 检查发布归档、CI 日志和 issue 模板。公开复现只用示例或经过检查的摘要；原始生产 trace、符号和签名材料由接入方保存。

开发顺序建议为 M0 评审 → M1 真机与协议验收 → M2 发布。最先需要维护者确认的是首版支持范围和数据接口；仓库归属与许可证可在对外发布前定案。
